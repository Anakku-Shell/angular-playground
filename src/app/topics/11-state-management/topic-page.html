State management

State that several components share needs one owner. Here the same cart is built twice: first as a plain service with signals, then with NgRx SignalStore (@ngrx/signals). The stores live in src/app/topics/11-state-management/stores/, the demos in demos/ and the presentational components in ui/.

A store service with signals

CartStore keeps the lines in a private writable signal and exposes a readonly view (asReadonly()) plus computed count and total. Its methods (add, remove, clear) are the only way to change the state. The badge injects the same store, so it updates without any input.

Code: stores/cart-store.ts, service-store-demo.ts, catalog.ts

  • This pattern is enough for most apps: no library, easy to test, and it is what many teams mean by "a service with signals". It replaces the older "service with a BehaviorSubject" pattern.
  • Update immutably (update(lines => [...lines, line])). Signals compare with ===: pushing into the same array does not notify anyone.
  • Container / presentational: the demo (container) talks to the store; ProductList and CartView only have inputs and outputs, so they are reused by the next demo unchanged.
  • Where it is provided decides its lifetime: providedIn: 'root' is one instance for the app (topic 05 shows the scopes).

The same cart with NgRx SignalStore

signalStore() builds the store class from features: withState (each property becomes a signal), withComputed and withMethods, where patchState writes new state. The component provides it in its own providers, so it gets a fresh cart that is destroyed with it. watchState logs every state change.

Code: stores/cart-signal-store.ts, signal-store-demo.ts

  • State is protected by default: patchState(store, …) only works inside the store, so components must go through its methods (like the private signal above).
  • patchState takes a partial object or an updater function (state) => ({ … }), and merges it one level deep.
  • What the library adds over a plain service: less boilerplate for big states, deep signals for nested objects, hooks, reusable features (signalStoreFeature), withEntities for collections and a Redux DevTools integration (from the community @angular-architects/ngrx-toolkit).
  • signalStore({ providedIn: 'root' }, …) makes a global store instead.

Async side effects with rxMethod

CatalogStore.search is an rxMethod: an RxJS pipeline (debounce, distinctUntilChanged, switchMap to the API) exposed as a method. In withHooks onInit, the store calls search(store.query) with the query signal, so every change of the query runs the pipeline. Loading, results and errors are all state.

Code: stores/catalog-store.ts, rx-method-demo.ts, catalog.ts (a fake API with a delay)

  • rxMethod accepts a value (runs once), a signal or an Observable (runs on each emission), and unsubscribes when the store is destroyed.
  • Catch errors inside switchMap. An error reaching the outer pipeline ends it, and the method stops working. tapResponse from @ngrx/operators packages this next / error handling.
  • No RxJS needed? signalMethod is the same idea for plain functions, and a resource / httpResource (topic 09) can live in a store too.

Local state with signalState

signalState is the state part of SignalStore without the class: one object, read through signals, changed with patchState. Nested objects become deep signals: state.filters.maxPrice() reads one field.

Code: signal-state-demo.ts

  • Good for a component with several related fields (filters, a wizard) that would otherwise be many separate signals.
  • patchState is shallow: to change filters.maxPrice, spread filters yourself.
  • Not everything is store state: form input, hover or "is this panel open" usually stay in the component.
