Dependency injection

A class asks for what it needs with inject(Token) and an injector supplies it. Injectors form a tree: an element injector for each component or directive that has providers, then the route and root (environment) injectors. The lookup walks up from the element that asks and stops at the first provider it finds. The code of each demo lives in src/app/topics/05-dependency-injection/demos/.

A class never creates its dependencies with new. It asks for them with inject(Something), and Angular decides which instance it gets. To answer, Angular walks up from the component that asks and takes the first provider it finds: 

 inject(Counter) in a component
   │  looks at its own element      providers / viewProviders
   ▼  then each parent element      providers: [Counter]   ← the first match wins
   ▼  then the route                providers: [...]
   ▼  then the app                  providedIn: 'root', app.config.ts
   ✗  nothing found                 NG0201 (unless optional: true)

So the same inject(Counter) can return one shared instance or a private one: it depends on where the provider is, not on the code that asks.

providedIn: 'root' vs component providers

In short

Counter is @Injectable({ providedIn: 'root' }): panels A and B find no provider on the way up, reach the root injector and share its single instance. Panels C and D each sit inside an <app-counter-scope> with providers: [Counter], so each gets its own instance. Press the buttons and compare the instance numbers.

  • The root instance lives as long as the app. Leave this page and come back: A and B keep their count, C and D start again at 0 (their instances were destroyed with the scopes).
  • providedIn: 'root' is the default choice for services: no registration needed, and a service nobody injects is removed from the bundle.
  • A component-level service is destroyed with its component: its ngOnDestroy and DestroyRef callbacks run. Root services are only destroyed with the app.
  • @Injectable() without providedIn does nothing by itself: some providers array must list the class, or injecting it throws NG0201.
  • Vue: provide()/inject() only look up the component tree. Angular adds the root and route injectors, and classes can be tokens.

providers vs viewProviders

In short

Both boxes provide a Counter and hold one panel in their own template plus one projected panel. With providers both panels share the box's instance. With viewProviders only the box's own view sees it: the projected panel keeps looking up from where it was written and reaches the root instance (the same number as panels A and B).

  • Use viewProviders when a component's internal services must not leak into content that users of the component project into it.
  • Projected content is created by the template that declares it, so its lookup starts there, not inside the component that displays it.

InjectionToken

In short

Values that are not classes (config objects, strings, functions, signals) need an InjectionToken as their key. PREFERS_DARK_SCHEME has a factory and providedIn: 'root', so it works with no provider: the factory injects DOCUMENT and wraps matchMedia in a signal. Angular's own settings are tokens too: <app-euro-price> provides DEFAULT_CURRENCY_CODE as 'EUR', and the currency pipe inside it follows.

  • Interfaces and type aliases do not exist at run time, so they cannot be tokens. Pair them with an InjectionToken<MyConfig>, or use an abstract class.
  • Wrapping browser globals (window, localStorage, matchMedia) in tokens makes them easy to replace in tests and on the server. This factory checks for matchMedia, which the test environment (jsdom) lacks.
  • The description string ('PREFERS_DARK_SCHEME') only appears in error messages. The token object itself is the key: two tokens with the same description are different.

useValue, useClass, useExisting, useFactory

In short

A provider is { provide: token, use…: … }. This demo registers all four kinds: a config object with useValue, MemoryLogger behind the abstract Logger with useClass, AUDIT_LOG as an alias with useExisting, and a Greeter built by useFactory. Writing to AUDIT_LOG lands in the Logger list (same instance). DEBUG_LOG is a second useClass, so it has its own list.

  • providers: [MemoryLogger] is short for { provide: MemoryLogger, useClass: MemoryLogger }.
  • useClass vs useExisting: useClass creates a new instance for that token; useExisting hands out whatever the other token resolves to.
  • Swapping implementations is the point: tests provide { provide: Logger, useValue: fakeLogger } and the code under test does not change.
  • Add multi: true to collect several providers of one token into an array (how HTTP_INTERCEPTORS and validators worked before functional APIs).
  • Legacy: factories received their dependencies through deps: [A, B]; with inject() inside the factory that is no longer needed.

Resolution modifiers: optional, self, skipSelf, host

In short

Each box provides itself as a Section and finds its parent with inject(Section, { skipSelf: true, optional: true }). The probes look up Section four ways. The first probe is written directly inside "Inner", so host finds it. The second lives in the template of <app-framed-probe>: host stops at that component, which provides nothing, and returns null, even though "Frame" is right above it.

  • optional: return null instead of throwing NG0201 when nothing is found. The type becomes T | null.
  • self: only the requesting element. skipSelf: start at the parent, the usual way to find "the enclosing one of me". Here it is required: without it a box would find itself while it is still being created, and throw NG0200 (circular dependency).
  • host: stop at the host element of the current template. At that host only its viewProviders count, not its providers.
  • Legacy: the @Optional(), @Self(), @SkipSelf() and @Host() parameter decorators on constructor parameters.

DestroyRef

In short

inject(DestroyRef).onDestroy(callback) registers cleanup for the current injection context. The ticker panel provides a Ticker service that starts a setInterval and clears it in onDestroy. Unmount the panel: the service is destroyed with it and the log shows both cleanups.

  • It works in components, directives, pipes and services, so cleanup sits next to the code that needs it instead of in a separate ngOnDestroy.
  • takeUntilDestroyed() (RxJS interop) uses the same DestroyRef to complete subscriptions: interval(1000).pipe(takeUntilDestroyed()).
  • onDestroy returns a function that unregisters the callback, for cleanup that finishes early.
  • In a root service, DestroyRef belongs to the root injector: the callback runs only when the whole app is destroyed.

The injection context

In short

inject() only works while Angular is creating something: in a constructor, a field initializer, a provider factory, or inside runInInjectionContext(). injectDocumentTitle() is an "inject function" that calls inject(), so the same rule applies. In a click handler it throws NG0203. Call it at creation and keep the result, or keep the Injector and use runInInjectionContext.

  • Other injection contexts: route guards and resolvers, interceptors, and the factory of an InjectionToken. That is why functional guards can call inject().
  • assertInInjectionContext(fn) at the top of an inject function gives a clear error that names it.
  • effect(), toSignal() and takeUntilDestroyed() follow the same rule: they need an injection context or an explicit injector / destroyRef option.
  • Legacy: constructor injection (constructor(private logger: Logger)). Migration: ng generate @angular/core:inject.
