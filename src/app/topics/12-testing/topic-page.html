Every test follows the same three steps: arrange (create what you test and give it fake dependencies), act (call a method, click, navigate) and assert (check the result). TestBed is Angular's tool for the first step: it builds a small app with only the providers each test needs. 

 arrange   TestBed.configureTestingModule({ providers: [fakes…] })
           const store = TestBed.inject(Store)  /  TestBed.createComponent(Comp)
 act       store.setCelsius(30)  /  button.click(); await fixture.whenStable()
 assert    expect(store.fahrenheit()).toBe(86)

The demos on this page are the subjects under test; the interesting code is in their .spec.ts files, in subjects/.

Running the tests

In short

{{ snippets.commands }}

ng test builds the specs with the same esbuild pipeline as the app and hands them to Vitest. Every *.spec.ts under src/ is a test file. Coverage uses @vitest/coverage-v8; open coverage/index.html after a run.

  • describe, it, expect, beforeEach and vi are globals (vitest/globals in tsconfig.spec.json). The syntax is close to Jasmine, so older Angular tests read the same.
  • Focus while you work: it.only / describe.only, or --include with a folder or file. Remove .only before committing.
  • TestBed is reset before every test: providers, components and services do not leak from one test to the next.

Component tests: inputs, outputs and model

In short

TestBed.createComponent renders the component into a detached DOM. Tests set inputs with fixture.componentRef.setInput, click real elements, then await fixture.whenStable() before reading the DOM again. To test [(value)] as a parent uses it, the spec renders a tiny host component. 

{{ snippets.component }}
{{ snippets.host }}
  • Zoneless fixtures run change detection on their own, like the app, but not synchronously. After an action, await fixture.whenStable() before reading the DOM. fixture.detectChanges() still exists for synchronous cases.
  • Test what the user sees (text, attributes, disabled state), not private fields. A refactor that keeps the behavior should keep the tests green.
  • An output() is an OutputRef: .subscribe() on it directly in the test, or use a host with (rated)="…".

Services with signals and computed

In short

A service needs no component: TestBed.inject(TemperatureStore) and call it. computed values are read synchronously right after a write. effects are scheduled, so the test calls TestBed.tick() to run them. 

{{ snippets.signals }}
  • it.each runs one test per row: good for boundaries like 9.9 / 10 / 25 °C.
  • A service that does not inject anything could be tested with a plain new; TestBed.inject works either way and keeps DI (inject()) working.

HTTP with HttpTestingController

In short

The demo calls DummyJSON. The spec replaces the backend with provideHttpClientTesting(): requests are captured, the test checks their URL, method and params, and answers with flush (data or an error status) or error (a network failure). 

{{ snippets.http }}
  • HttpClient is lazy: subscribe (here firstValueFrom) before expectOne, or there is no request to find.
  • httpMock.verify() in afterEach fails the test if a request was sent that nobody expected.
  • API_BASE_URL is a token, so the test provides its own base URL. Tokens are the usual way to make configuration testable.

Mocking dependencies through DI

In short

Greeting reads the hour from a Clock service, not from new Date(). The spec provides a fake clock with useValue, so each test picks the hour. vi.spyOn is the lighter option: keep the real service, stub one method and check how it was called. 

{{ snippets.mocking }}
  • Configure providers before the first createComponent / inject; after that TestBed is frozen for this test.
  • Other options: useClass (a fake class, like the InstantCatalogApi in topic 11), TestBed.overrideComponent to change a component's own providers or imports, and vi.useFakeTimers() to control Date and timers globally.

Routes with RouterTestingHarness

In short

{{ snippets.router }}

RouterTestingHarness hosts a router outlet and navigates it with the real routes. navigateByUrl(url, Component) also checks which component was activated and returns it, so the test can read the input bound from :id. Clicking a routerLink and awaiting the fixture moves the router like in the app.

  • Use the same router features as the app (withComponentInputBinding() here), or inputs bound from the URL stay empty in tests.
  • Guards and resolvers are plain functions: test them through navigation with the harness, or call them inside TestBed.runInInjectionContext.
