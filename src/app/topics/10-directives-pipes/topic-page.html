Directives & pipes

A directive adds behavior to an element it does not own; a component is a directive with a template. A pipe transforms a value in the template. The directives live in src/app/topics/10-directives-pipes/directives/, the pipes in pipes/ and the demos in demos/.

Attribute directive with inputs: highlight

Highlight listens to mouseenter / mouseleave on its host and binds the host's background. Its main input has the same name as the selector, so appHighlight="pink" both applies the directive and configures it.

Code: directives/highlight.ts, highlight-demo.ts

  • Selector [appHighlight] = "any element with this attribute". Directive selectors are camelCase attributes with the app prefix; component selectors are kebab-case elements.
  • Host bindings and listeners go in the host metadata: '[style.backgroundColor]': 'color()', '(mouseenter)': 'onEnter()'. @HostBinding and @HostListener still work (and are common in v19 code) but the style guide prefers host.
  • Directive inputs are ordinary input() signals, so computed works on them. A directive is used by adding it to the component's imports, like a component.
  • Avoid touching the DOM directly (ElementRef.nativeElement.style…): host bindings are declarative, work with SSR and are cleaned up for you.

Host listeners and creating a component: tooltip

Tooltip reacts to mouse, focus and Escape on its host. A directive has no template, so to show something it creates a component (TooltipBubble) with ViewContainerRef.createComponent() and passes it inputs with setInput(). It also binds aria-describedby so screen readers read the text.

Code: directives/tooltip.ts, tooltip-demo.ts

  • Directive vs component: use a directive to add behavior to elements that someone else renders (any button, any input). Use a component when you own the markup and styles. A directive cannot have a template or styles.
  • Listen to focus as well as hover: a tooltip only on mouseenter is invisible to keyboard and touch users.
  • inject(ElementRef) gives the host element, inject(ViewContainerRef) the place next to it where views can be inserted.
  • Real apps use the CDK (@angular/cdk/overlay) or a UI library for tooltips: positioning, scrolling and collisions are harder than this demo shows.

exportAs, global listeners and outputs: dropdown

Dropdown holds the open state. exportAs: 'appDropdown' lets the template grab the directive instance with #menu="appDropdown" and call menu.toggle(). It listens to document:click and document:keydown.escape to close, and reports why through a closed output.

Code: directives/dropdown.ts, dropdown-demo.ts

  • #ref alone gives the element (or the component); #ref="exportAsName" gives a directive on it. ngModel and ngForm work the same way.
  • Global targets in host listeners: document:, window: and body:. Angular removes the listener when the directive is destroyed.
  • Key filters work in host listeners too: keydown.escape, keydown.enter, keydown.control.s.

Composition with hostDirectives

<app-tag> declares hostDirectives: [Highlight, Tooltip], so every tag gets both behaviors with no attributes in the template. The directives' inputs are exposed under new names (color, hint), and the component injects Highlight to show the dot while hovered.

Code: host-directives-demo.ts

  • Composition instead of inheritance: extending a base component class shares code but not host bindings cleanly, and a class can only extend one.
  • Inputs and outputs of a host directive are hidden unless listed: inputs: ['appTooltip: hint']. A required input must be exposed.
  • Host directives are applied statically (always, not conditionally) and must be standalone. Their selectors are ignored.

A custom structural directive

*appHasRole="'editor'; else readOnly" renders its content only for editors and admins. The * wraps the element in an <ng-template>; the directive injects that TemplateRef and a ViewContainerRef, and an effect stamps the template (or the else template) when the role changes.

Code: directives/has-role.ts, session.ts, structural-demo.ts

  • Since v17, @if, @for and @switch cover what most structural directives did. Custom ones are still handy for app-specific rules like permissions or feature flags.
  • Microsyntax: in *appHasRole="x; else y", else maps to the input appHasRoleElse (directive name + capitalized key).
  • Hiding a button is UX, not security: the server must check permissions too.
  • A directive can pass variables to its template through a context (createEmbeddedView(tpl, { $implicit: value }), read with let x). A static ngTemplateContextGuard types them.

A custom pipe with arguments

TruncatePipe implements PipeTransform. The first parameter of transform is the value on the left of the |; each : arg fills the next parameter, and parameters with defaults are optional.

Code: pipes/truncate-pipe.ts, truncate-demo.ts

  • Pipes can be chained (name | truncate: 10 | uppercase) and can inject() services (e.g. the current locale).
  • The pipe name is camelCase and has no prefix requirement, but it must be unique in the component's imports.
  • Built-in pipes (date, currency, async…) are in topic 01.

Pure vs impure pipes

Both pipes filter the same array. Press Add with push(): the array changes but its reference does not, so the pure pipe keeps its old result. The impure pipe runs on every check and shows the new item. Add as a new array updates both.

Code: pipes/filter-pipe.ts, pure-impure-demo.ts

  • Pure pipes are memoization: Angular calls transform only when an argument changes (===). A method call such as filter(items) in an interpolation runs on every check instead.
  • Keep pipes pure and update data immutably (a new array or object). Signals push you in the same direction: signal.set([...list, item]).
  • Impure pipes (pure: false) run on every change detection of the component, so keep them cheap. async is the best-known impure pipe.
  • With signals, derived data often fits better in a computed() in the class; a pipe is for formatting reused across templates.
