Observable vs Promise

In short

Press new Promise(): its code runs at once. Press new Observable(): nothing runs until subscribe(), and it runs again on every subscribe. The Observable emits three values over time; unsubscribe() stops it early and runs its teardown.

  • A Promise is eager (starts on creation), gives one value and cannot be cancelled. An Observable is lazy, can emit many values and is cancelled by unsubscribing.
  • That is why http.get() sends nothing until something subscribes: forgetting to subscribe (or to use | async / toSignal) is a classic "my request never fires" bug.
  • Each subscribe runs the Observable again (it is cold): two subscribers to an HTTP Observable send two requests. See shareReplay below.
  • Need a Promise? await firstValueFrom(obs$). The old toPromise() is deprecated.

Flattening operators: switchMap, mergeMap, concatMap, exhaustMap

In short

Each click starts a fake request that answers after one second. An operator that maps a value to another Observable has to decide what to do when a new click arrives while a request is still running. Click one button three times quickly and compare the lanes.

  • Rule of thumb: reads that follow user input → switchMap; independent writes → mergeMap; writes whose order matters → concatMap; a submit button that must not fire twice → exhaustMap.
  • Never subscribe inside a subscribe. Nested subscriptions are not cancelled and have no order guarantees; a flattening operator is always the answer.
  • map transforms each value, filter drops values. Both appear in the search demo below.

Interceptors: auth header, logging, global errors

In short

Every request goes through three functional interceptors, in order: authInterceptor adds Authorization: Bearer … (only for our API), loggingInterceptor fills this table and errorInterceptor reports errors app-wide and rethrows them. The 503 button retries twice: the log shows three attempts, because retry() subscribes again and every attempt runs the whole chain.

  • An interceptor is a function (req, next) => next(req). Requests are immutable: change them with req.clone({ setHeaders: … }).
  • inject() works in the interceptor body, not inside the RxJS callbacks: call it first and keep the reference.
  • Order matters: requests go through the array top to bottom, responses come back bottom to top. Here logging comes after auth so it sees the header.
  • HttpContextToken passes per-request options to interceptors: the search below sets SKIP_GLOBAL_ERROR because it shows its own error.
  • Legacy code uses class interceptors (HttpInterceptor + HTTP_INTERCEPTORS multi-provider). They need withInterceptorsFromDi().

Typed API service, async pipe vs toSignal, shareReplay

In short

ProductsApi wraps the endpoints: components call api.list(3), not URLs, and http.get<ProductPage>() types the response. Here the same list is rendered twice, once with the async pipe and once with toSignal. The cold stream sends one request per consumer; the shareReplay one sends one in total.

  • http.get<T>() is a cast, not a check: the server can send anything. Validate at the boundary (e.g. with a schema library) when the data matters.
  • async pipe: subscribes in the template, unsubscribes when the view goes away, returns null until the first value. toSignal: subscribes in the class (injection context), gives a signal you can use in computed and effect, returns undefined until the first value (or use initialValue). New code prefers toSignal.
  • Unsubscription rules: async, toSignal, httpResource clean up for you. A manual subscribe() to something that does not complete (valueChanges, interval, router events) needs takeUntilDestroyed(). HTTP completes after one response, but unsubscribing still aborts an in-flight request when the user leaves.
  • shareReplay({ bufferSize: 1, refCount: true }): without refCount the source stays subscribed forever, even after every consumer is gone.

Search as you type

In short

The input's valueChanges goes through map (trim), debounceTime(300), distinctUntilChanged(), filter and switchMap to the API. Each request becomes a loading, success or error state, and toSignal hands the latest one to the template. Type fast and compare the request count with the number of keystrokes. The API adds 500 ms of delay so the loading state shows.

  • catchError goes inside the switchMap. An error that reaches the outer stream ends it, and the search box silently stops working.
  • Model the UI as one union type (idle | loading | success | error) instead of separate loading / error / data flags that can contradict each other.
  • switchMap aborts the previous request, so a slow old response never overwrites a newer one (a race condition that mergeMap would have).
  • retry({ count, delay }) resubscribes on error; only use it for requests that are safe to repeat (GET, not a payment).

httpResource (experimental)

In short

httpResource(() => url) is resource() backed by HttpClient: when a signal read in the URL function changes, it aborts the running request and sends a new one. Status, value, error and the HTTP status code are all signals, so there is nothing to subscribe to. Id 999 answers 404.

  • httpResource is experimental (since 19.2): the API may change. Current codebases mostly use HttpClient Observables.
  • It is for reading data (GET). Use HttpClient for POST, PUT and DELETE.
  • It uses HttpClient, so interceptors and provideHttpClientTesting work. Pass { parse: schema.parse } to validate the response and defaultValue to avoid undefined.
  • Read error() or hasValue() before value(): reading the value of a failed resource throws.
