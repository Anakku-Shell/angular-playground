Component communication

How a parent passes data down to its children, how children report events up, how a parent fills a child's template with its own content, and how components that are not directly related share state. The code of each demo lives in src/app/topics/03-component-communication/demos/.

input(): data from parent to child

readonly value = input(0) declares an input and returns a read-only signal: the child reads value(), the parent binds [value]="...". input.required<T>() has no default, and the template compiler reports any usage that does not set it. Options: transform converts the incoming value, and alias gives the input a different public name (here caption).

Code: inputs-demo.ts / .html, inputs/progress-bar.ts

  • A static attribute (max="250") always passes a string. The built-in numberAttribute and booleanAttribute transforms let a component accept both max="250" and [max]="250", and a bare striped.
  • Inputs are read-only in the child: there is no value.set(). Derive new values with computed() (like percent here), or use model() when the child must write back.
  • Avoid aliases unless you need them (e.g. keeping a public name while renaming the field). Do not name an input like a native attribute such as title: the static attribute stays on the host element too, and shows a tooltip over the whole component.
  • Legacy: @Input() value = 0; is a plain field, not a signal. Changes were seen through ngOnChanges or setters.

Deriving from inputs: computed and linkedSignal

The picker gets its options as an input and keeps the selected one as local state. That state must be writable (the user picks) but must also reset when the options change. linkedSignal(() => this.options()[0]) does both: it is a writable signal whose value is recomputed whenever the signals it reads change. The summary line is a plain computed(), read-only.

Code: linked-demo.ts / .html, linked/option-picker.ts

  • signal(this.options()[0]) in a field would throw NG0950: required inputs have no value yet while the class is being constructed. Read inputs inside computed, linkedSignal, templates or lifecycle hooks.
  • linkedSignal({ source, computation: (options, previous) => ... }) can keep the previous choice when it is still valid. The Signals topic covers it.
  • linkedSignal is stable since v20 (developer preview in v19). Before it, the usual pattern was ngOnChanges resetting a field.

output(): events from child to parent

readonly rated = output<number>() declares a custom event. The child calls rated.emit(4), and the parent listens with (rated)="onRated($event)", where $event is the payload. The rating receives its value as an input and never changes it: it reports the click and the parent decides. This "data down, events up" flow keeps the state in one place.

Code: outputs-demo.ts / .html, outputs/star-rating.ts

  • Outputs do not bubble: only the direct parent can listen. Deeper trees must forward the event at each level (see the tree demo below).
  • Name outputs after what happened (rated, cleared), without an on prefix. Avoid native event names like change or click: a native event bubbling from inside the child would reach the same (change) listener.
  • An input value plus an output valueChange is exactly what [(value)] expects. model() declares both at once.
  • Legacy: @Output() rated = new EventEmitter<number>();. output() is not an RxJS Subject; it has no pipe().

model(): two-way binding on a custom component

readonly value = model(1) is an input the child may also write: value.set() updates the child and emits valueChange. With [(value)]="quantity" the parent's signal follows. With a one-way [value]="quantity()" the child changes only its local copy, and the parent's next change overwrites it. Use the steppers, then the button.

Code: model-demo.ts / .html, model/quantity-stepper.ts

  • Pass the signal, not its value: [(value)]="quantity". A plain field works too ([(value)]="count").
  • Gotcha: "Parent: set to 1" does nothing to the one-way stepper when the parent already holds 1. A signal set to the same value does not notify, so the input is not updated.
  • Use model() for form-like controls (steppers, toggles, pickers). For the rest, prefer an input plus a named output: the child then asks, and the parent decides.

Content projection: ng-content

A component places <ng-content /> where the content written between its tags should appear. With several <ng-content select="..."> slots, each one takes the elements that match its CSS selector, and the one without select takes the rest. Content inside <ng-content> is a fallback, shown when nothing is projected into that slot. ngProjectAs makes an element match a selector it would not match on its own, typically an <ng-container> grouping several elements.

Code: projection-demo.ts / .html, projection/callout.ts, projection/panel.ts / .html

  • This page is built with it: app-demo-card has demo-title and demo-body slots plus a default slot.
  • Projected content is created by the parent, even if the child never shows it (e.g. <ng-content> inside an @if). For lazy content, the child takes an <ng-template> and renders it with ngTemplateOutlet.
  • Content is projected once: an <ng-content> inside an @for does not repeat it.
  • The child's encapsulated styles do not reach projected elements. Style them from the parent, or with global styles (this project styles [demo-title] in styles.scss).

Queries: viewChild, viewChildren, contentChild

Queries give a component direct access to elements and child components. viewChild('search') finds a template reference in the component's own template, viewChildren(Stopwatch) finds every instance of a component type there, and contentChild('control') searches the content projected into it. All of them return signals that update when the matching elements change (add or remove a lane).

Code: queries-demo.ts / .html, queries/stopwatch.ts, queries/labeled-field.ts

  • viewChild.required() removes undefined from the type and throws if nothing matches. The plain version returns T | undefined, useful when the element is inside an @if.
  • Query results exist only after the view is created: read them in event handlers, computed, effect or afterNextRender, not in the constructor.
  • Calling child methods through a query couples the parent to the child's API. Prefer inputs and outputs; use queries for DOM work (focus, measuring) or imperative components like players and timers.
  • Options: { read: ElementRef } gets the host element of a matched component; contentChildren(X, { descendants: true }) also searches nested content.
  • Legacy: @ViewChild('search') search!: ElementRef;, available from ngAfterViewInit (and @ContentChild from ngAfterContentInit).

Parent ↔ child ↔ grandchild

The parent owns the tasks. Each app-task-list receives its tasks as an input and passes each one to an app-task-item. When a checkbox changes, the item emits toggled, the list re-emits it, and the parent updates its signal. The new array then flows back down and every level re-renders.

Code: tree-demo.ts / .html, tree/task-list.ts, tree/task-item.ts

  • This is the smart / presentational split: the parent holds state and logic, the list and items only display inputs and emit outputs. Presentational components are easy to reuse and to test.
  • Every extra level has to declare and forward the same input and output ("prop drilling"). Past two or three levels, share the state through a service instead.
  • Update state immutably ({ ...task, done: true }). Mutating the object in place keeps the same reference, and an OnPush child would not re-render.

Siblings: sharing state through a service

app-product-picker and app-cart-summary have no bindings between them. Both call inject(CartStore) and get the same instance, because CartStore is provided once by their common parent. The picker calls store.add(); the summary reads store.count() and store.total(), which are signals, so it re-renders on its own.

Code: siblings-demo.ts, siblings/cart-store.ts, siblings/product-picker.ts, siblings/cart-summary.ts

  • Keep the writable signal private and expose asReadonly() and computed values plus methods. Only the store can change the state.
  • providedIn: 'root' would make one cart for the whole app. Providing it in a component scopes it to that component and its children. The Dependency injection topic covers both.
  • Older code shares state through a service with an RxJS BehaviorSubject and the async pipe. Signals now fill that role.
