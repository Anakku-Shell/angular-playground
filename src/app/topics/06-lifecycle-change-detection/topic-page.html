Lifecycle & change detection

Angular creates a component, sets its inputs, renders its view and destroys it, calling lifecycle hooks along the way. Change detection is the pass that refreshes views after state changes. In v21 it is zoneless: Angular only refreshes when something tells it to, and OnPush components are only checked when they are marked. The code of each demo lives in src/app/topics/06-lifecycle-change-detection/demos/.

"Change detection" is how Angular keeps the DOM in sync with your data: it re-reads the bindings of a component and updates what changed. Two questions matter: when does a refresh happen, and which components does it check? 

 something tells Angular              then Angular checks
 ───────────────────────              ───────────────────
 a signal read by a template    ─┐
 an event bound in a template    ├──▶  the components marked dirty (OnPush),
 markForCheck() / async pipe     │     re-reads their bindings and updates the DOM
 an input set, a view added     ─┘
 setTimeout, fetch, a plain field: nothing (zoneless)

The first two cards are about a component's life (hooks and render hooks); the last two about refreshing it (OnPush and zoneless).

Lifecycle hooks

In short

The child logs every hook it goes through. Creating it runs the constructor, ngOnChanges (first change), ngOnInit, ngAfterContentInit and ngAfterViewInit. Changing its input runs ngOnChanges again, with the previous and the new value. Destroying it runs ngOnDestroy and the DestroyRef.onDestroy callbacks.

  • Constructor vs ngOnInit: inputs are set only before the first ngOnChanges. Reading a required input in the constructor throws NG0950. Use the constructor for inject() and setup that does not need inputs.
  • ngOnChanges also fires for signal inputs, but computed() or effect() on the input is usually clearer. It never fires for changes inside an object passed by reference.
  • ngDoCheck, ngAfterContentChecked and ngAfterViewChecked run on every check of the component. Keep them cheap, or avoid them.
  • ngAfterViewInit is the classic place for DOM work and @ViewChild reads. With signal queries and afterNextRender (next card) it is rarely needed.
  • ngOnDestroy and DestroyRef.onDestroy do the same job; DestroyRef keeps the cleanup next to the code that needs it and also works in inject functions.

afterNextRender and afterEveryRender

In short

Both run after Angular has updated the DOM, so they can measure or change elements. afterNextRender runs once: here it measures the list after the first render. afterEveryRender runs after every render of the app: here it keeps the list scrolled to the bottom and counts renders. "Unrelated update" does not touch the list, yet the count still goes up.

  • Stable since v20. afterEveryRender was called afterRender in v19 (developer preview then).
  • Split DOM work into phases (earlyRead, write, mixedReadWrite, read) so reads and writes of all callbacks are batched and the browser does not recompute layout between them.
  • They are browser-only: during server rendering they never run. That makes them the safe place for window, document and third-party DOM libraries.
  • Do not set signals in afterEveryRender: the change schedules another render, which runs the hook again. afterRenderEffect() is the signal-aware variant that only re-runs when the signals it reads change.
  • They are registered in an injection context and cleaned up with the component.

OnPush: what refreshes a component

In short

The parent passes a user object to an OnPush child. "Mutate" changes a field inside the same object: the parent re-renders (the click was in its template) but the child keeps showing the old value, because its input still holds the same reference. "Replace" creates a new object, so the child is checked. After a mutation, "markForCheck()" or a click inside the child also shows the new value.

  • An OnPush component is checked only when: an input gets a new value (compared with ===), an event fires in its template, a signal its template reads changes, an async pipe in it emits, or markForCheck() is called.
  • Treat inputs as immutable: produce new objects and arrays ({ ...user }, [...list, item]) instead of mutating them.
  • markForCheck() marks the component and its ancestors, so the next run reaches it. detectChanges() checks the component and its children right away, synchronously.
  • The other strategy, Eager, checks the component on every run, whether or not it was marked. It is the default when changeDetection is omitted. v21 renamed it: ChangeDetectionStrategy.Default still works but is deprecated.

Zoneless change detection

In short

Without zone.js, nothing watches setTimeout, promises or fetch. Angular refreshes only when it is notified. A plain field changed in a timeout stays stale on screen. The same change followed by markForCheck() shows up, and so does a signal. Press "Plain field in the click handler" after a stale update: the event schedules a refresh, and every earlier change appears at once.

  • What schedules change detection without zone.js: a signal read by a template changes, a template event handler runs, markForCheck() is called, an async pipe emits, a view is attached or removed, or setInput() is called on a component ref.
  • With zone.js (the default before v21), zone.js patched every async browser API and ran change detection after each one. The plain field would have updated. Zoneless apps skip that overhead and drop zone.js from the bundle.
  • Zoneless is stable since v20.2 and the default for new apps in v21. Older apps opt in with provideZonelessChangeDetection() and remove zone.js from the polyfills.
  • Migrating: code that relied on zone.js (plain fields set in subscriptions, timers or promises) must switch to signals, the async pipe, toSignal() or markForCheck(). OnPush components are usually ready already.
